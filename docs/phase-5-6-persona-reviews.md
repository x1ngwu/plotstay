# 阶段 5.6：角色评价与回复（产品规则与实施方案）

2026-10-08：阶段 5.5 已获用户确认关闭（实现提交 `7ba1bfe`，已推送并部署）。5.6 的角色创作方向及六项产品选择已确认（1A 至 6A），以下整理实施方案；尚未启动功能开发，未研究 moonmistvalley，没有修改运行代码或数据库。用户要求后续问题使用普通文本，不使用 Codex 提问功能。

## 已确认的方向

- 公开评价由用户选择的虚构马甲角色发表，不直接以用户本人身份出现。
- 一个用户可以拥有多个虚构角色；提供住宿、活动、服务与发表评价应使用一致的角色概念。
- 用户进一步确认采用“角色创作、自由评价”的方向：不以模拟预订或行程结束作为发表前提，评价是世界内的创作内容。
- 既有计划允许内容作者及其他用户创作评价，不能未经确认改成禁止作者为自己创作的条目写评价。
- 账号承担所有权、编辑权限和审核责任；角色承担故事内身份。切换角色不会增加后台权限。
- 沿用已确认的审核后公开原则。5.5 的后台手记、既有评分和历史数据继续保留。
- 用户确认 1A：使用已有或管理员创建的账号，提供面向普通用户的“我的角色”和评价入口；不要求进入内容管理后台，公开注册留后续。
- 用户确认 2A：角色属于用户，可以跨世界使用；住宿、活动、服务和评价各自归属具体世界。
- 用户确认 3A：同一角色对同一条目只保留一篇评价，可以修改并重新审核，只贡献一份评分。
- 用户确认 4A：每篇评价允许一条提供者回复，使用对应房东／向导／服务提供者角色署名；可以修改并重新审核，不做多层讨论串。
- 用户确认 5A：角色保存后即可写评价草稿；首次发表时角色资料与评价一同送审，全部通过后才公开，无需先等待角色单独获批再创作。
- 用户确认 6A：旧评价和回复保留发布时的角色名字、头像；角色改名换头像用于之后发表的内容，不自动更新旧署名。历史旅行凭条始终不变。

## 现有基础与缺口

数据库已有 `personas.owner_id`、多语言 `profiles` 和 `approved`；内容已有 `author_id`、可选 `persona_id`。创建内容会核对角色归属与批准状态，但当前创建接口要求世界成员权限，不能直接当作普通用户投稿接口。

人物展示尚未统一由角色驱动：房东／向导等姓名与介绍，以及手记中的旅客姓名，仍包含内容版本内的字段。已有角色关系不等于已经完成角色切换和身份一致性。关联角色、正文展示字段和历史快照的优先级需要明确。

阶段 5 使用独立游客 Cookie 签发模拟预订，不能将它当成账号登录或已有可管理角色的证明。预订表预留的 user/persona 引用也不代表账号认领、自助注册和角色预订链路已经开放。

当前条目总分取所有已发布手记中已填总分的平均数；分项分别统计。住宿房东卡片的评分和评价数量目前是手工配置，尚未汇总房东旗下条目。

## 身份与交互设计

1. 以同一套角色资料管理旅客、房东、向导和服务提供者；这些是角色在某次内容中的身份，不把角色永久锁定为一种职业。
2. 发评价前显示“以谁的身份发表”，列出当前用户可用的角色；选中后显示姓名、头像和简短设定，再填写正文和评分。未创建角色时引导创建，不自动把账号昵称当作角色名。
3. 评价同时保留实际作者和角色引用；公开展示角色，管理界面可追溯作者，不因多个角色属于同一账号就在公开页面自动串联身份。
4. 按用户确认的 6A，发布时保存角色展示资料快照，角色后续改名不悄悄改写旧评价。既有评价不按同名人物自动绑定或批量改写。
5. 已确认回复显示对应提供者角色，一篇评价只有一条提供者回复，可修改并重审。需要检查实际操作者是否有该条目的回复权限，不能仅因拥有任意角色就使用提供者身份。
6. 角色资料与投稿状态分别管理；角色被停用后禁止新发言，已有评价是否隐藏通过明确审核操作处理，不默认删除历史。

## 产品规则

### 角色评价与分数的含义

用户已确认角色创作方向，评价定位为世界内创作。评分沿用现有“每篇已发布且带评分的评价参与均分”的规则，不新增按真实账号或订单加权。一个作者用多个角色创作不同立场的评价符合原产品方向。同一角色对同一条目仅一篇评价；已有评价时进入编辑，不能通过重复提交、多标签页或新建草稿增加第二份评分。修改重审期间继续展示原已发布版本和分数，新版本获批后替换，回复不参与计分。

评分表达故事中角色的主观体验，不作为独立真实消费者信誉指标。第一版建议保留住宿房东卡片评分的现有配置方式，不顺带引入跨条目汇总或排名规则。

### 是否必须预订

已确认不强制预订，不要求等待入住、退房或活动结束；直接选择角色即可开始创作。既有计划中“预订可用于评价资格”的设想在 5.6 不作为硬性门槛。模拟预订仍保留原玩法，可选的凭条关联只是后续建议，不是本次已确认范围；历史凭条不可改写。

### 角色归属与进入方式

已确认角色属于账号，使用已有或管理员创建的账号。用户登录后通过正常账户菜单进入“我的角色”，从详情进入评价创作，不需要后台内容编辑权限。未登录可阅读并引导登录，不开放游客 Cookie 创建角色、公开注册或订单认领。普通用户可向可投稿世界提交评价，不因此获得其他内容编辑、审核或世界管理权限；具体接口不能直接复用要求世界成员身份的后台写入入口。

已确认角色跨世界复用，不为每个世界强制重复创建角色；世界管理员审核本世界内容是否符合设定，不能因此取得跨世界角色所有权或改写其他世界内容。不因头像或名字相同推断为同一角色。

## 建议的页面与状态流程

- 账户菜单提供“我的角色”“我的评价”；无需进入后台。角色资料第一版建议姓名、头像、简短设定／简介，沿用中英结构；具体填写和缺译提示随表单设计落实。
- 三类详情的评价区域提供“以角色写评价”：登录 → 选择角色 → 若已评价则编辑，否则新建 → 保存草稿／预览 → 提交审核 → 公开。
- “我的评价”显示目标条目、署名角色、草稿／待审核／已发布／退回状态及审核说明。编辑已发布评价不会立即替换公开版本，退回也不抹掉原发布。
- 提供者在有权限的条目评价下回复，界面固定显示本次提供者身份，不能随意选择另一个角色冒充。回复保存和审核独立于评价；评价不可见时回复也不公开。
- 普通用户无法给他人的角色发言或编辑他人的评价。跨世界角色的可用性和各世界审核权限分别校验。
- 原有未绑定角色的后台手记继续展示与计分，不按姓名自动绑定；已绑定角色的旧数据需在迁移前检查重复关系，不能删除或改写历史来满足唯一约束。

## 角色审核与署名历史

1. **一次送审。** 用户保存角色即可写草稿，一次提交引用确定的角色资料版本与评价版本。角色和评价都通过审核才允许首次公开；其中一项待审或退回时，界面明确显示原因。已获批且未修改的角色版本无需为每篇评价重复审核。
2. **审核权限沿用既有边界。** 共用角色资料沿用网站管理员审核边界，世界管理员负责本世界评价／回复；网站管理员可在同一审核流程处理两者。一次送审不意味着世界管理员自动获得跨世界角色管理权。未审角色仅能用于所属用户的草稿与受保护预览，不能通过公开接口读取。
3. **审核版本固定。** 送审后修改角色或评价不得悄悄替换审核对象；需要重新提交或明确保留先前送审版本。发布检查匹配的获批版本，不能拼接尚未获批的最新资料。
4. **历史署名固定。** 每个评价／回复发布版本保存角色 ID、已审资料版本及用于展示的名字、头像等。旧版恢复必须同时恢复旧署名；公开读接口不将当前 persona 资料覆盖到历史署名上。头像需保留可稳定读取的版本化资源或引用，不能只保存一个可被覆盖内容的 URL 就宣称历史头像固定。
5. **修改评价与自动更新区分。** 单独修改角色不会更新旧内容。用户主动编辑并重新发布评价／回复时，预览清楚显示本次署名及正文；获批后形成新发布版本，旧版本仍保留。稳定角色 ID 用于判定“同角色同条目一篇评价”，改名不产生新的评价资格。

## 验收要求

- 两个普通账号各自拥有多个角色：角色、草稿、预览及编辑相互隔离；跨世界使用同角色成功，世界审核权限不跨界。
- 未预订用户可以提交评价；匿名用户需登录；游客预订 Cookie 不能冒充用户账号或取得角色权限。
- 未批准角色保存后即可创作；一次送审引用固定版本；角色或评价任一未批准时首次发布失败；退回可修改再提交。
- 同角色同条目并发新建只产生一个评价身份；重试幂等；修改或改名不增加评价数。同用户的不同角色可分别评价。
- 仅当前已发布且带评分的评价参与统计。草稿、退回及回复不影响评分；新版本发布和历史恢复正确替换当前贡献。
- 修改角色名字、头像后旧评价／回复和旧凭条不变；新发布正确使用本次已审署名，恢复旧版同时恢复其署名。
- 回复身份不可冒用，同评价并发回复不产生第二条；提供者、内容编辑和审核权限分别校验。
- 三类内容、中英界面、缺译回退、列表分页、手机宽度、会话过期保留输入及并发冲突均覆盖；新增测试纳入 `npm test` 和 `npm run test:e2e`。
- 旧后台手记、公开分数、已发布内容与历史凭条保持兼容；使用原库和数据卷，只做增量迁移，不重跑 seed。
- 按 operations.md 构建并更新开发域名；保持 Basic Auth、`SITE_INDEXABLE=false`、noindex、禁止抓取以及私人页面／预览的权限和缓存隔离。
