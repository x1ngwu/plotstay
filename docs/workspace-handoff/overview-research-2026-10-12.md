# 工作台首页参考调研与设计复核

日期：2026-10-12。对象：Plotstay 中英文工作台概览。依据：[已确认首页方案](overview-experience-spec.md)。

**性质：调研结论与讨论记录。** 用户授权寻找更好的方案、指出遗漏；调研后的确认状态见下方，各节保留原建议及最新答复。未确认细节不自动生效，不启动应用开发。

**后续确认：** R-01 的优先顺序和“可回复”已确认，收起提醒留远期；R-02 已确认；R-03 可信任务依据获认可，两个范围页签仍在讨论；R-05 加号语义已确认。已同步 [首页方案](overview-experience-spec.md)。R-04、R-06 新增细节仍为建议。

## 1. 结论

现有方向有充分的同类产品依据：以可操作事项、本人未完成工作、最近进展和常用空间组织个人首页，符合内容管理和协作产品常见的组织方式。角色／项目／世界／互动四组，以及具体左右栏位置，是结合 Plotstay 对象关系作出的设计选择，不能称为通用行业标准。

建议保留整体架构，继续细化任务归属、可选互动、版本状态和导航语义。官方案例能证明这些设计模式被实际采用；是否适合 Plotstay 的具体用户，还需用真实任务和不同数据量的原型验证。

## 3. 最值得参考的产品

### 3.1 Asana：个人首页的任务与继续工作

**官方事实：** Home 提供任务、近期项目、状态更新与快捷入口，也能恢复未发送的评论草稿。My Tasks 汇总分配给当前用户的任务；Inbox 承载相关更新。[Asana Home](https://asana.com/features/project-management/home)、[Asana My Tasks](https://asana.com/features/project-management/my-tasks)

**对 Plotstay 的判断：** 适合作为首页整体组织参考，尤其支持“互动草稿也属于继续工作”。个人任务应有明确的本人关系，不能用“有访问权限”替代任务归属。Plotstay 不需要因此引入任务分派系统或可拖拽组件。

**视觉参考：** [官方首页示意](https://assets.asana.biz/transform/23415d9c-d5d5-4dba-9f1a-9966eab071e1/web-features-hometab-header-2x-En-us?format=webp&io=transform%3Afill%2Cwidth%3A2560)。已查看：左侧任务列表与右侧项目入口分开，任务附近有项目归属；可借鉴扫描层级，不必复制大问候区、背景和统计。

### 3.2 Strapi：内容主体、类型、状态与时间

**官方事实：** 后台首页区分最近编辑与最近发布；最近编辑项包括内容类型、状态和更新时间。官方截图把这些字段与名称分列呈现。[Strapi 首页说明](https://docs.strapi.io/cms/admin-panel-customization/homepage)

**对 Plotstay 的判断：** 最适合参考单条内容的排版：主体名称醒目，归属、类型、状态和时间各有位置。Strapi 的“最近编辑”不等同于我们的“尚未完成”，不能直接搬用它的收录条件。

**视觉参考：** [官方后台首页截图](https://docs.strapi.io/img/assets/admin-homepage/admin-panel-homepage.png)。已查看：内容使用紧凑列表；全站统计与部署组件具有 Strapi 的产品背景，不能据此给 Plotstay 首页增加相同模块。

另一个相关机制是区分未发布草稿、已发布无改动，以及已发布但有新修改。它提示我们同时表达公开状态和当前修改状态。[Strapi Draft & Publish](https://docs.strapi.io/cms/features/draft-and-publish)

### 3.3 Confluence：常用空间与完整空间目录

**官方事实：** 提供最近访问、收藏空间的快速导航；“查看全部空间”列出有权查看的空间。新导航把个人入口与空间入口保留在侧栏。[空间导航](https://support.atlassian.com/confluence-cloud/docs/navigate-spaces/)、[新版导航](https://support.atlassian.com/confluence-cloud/docs/what-is-the-new-navigation-in-confluence/)

**对 Plotstay 的判断：** 与“常用世界＋所有世界”最接近。常用入口负责快速返回，完整目录负责寻找；目录可见范围与管理权限不同。需明确固定和最近访问的区别，避免自动排序让用户固定的位置跳动。

### 3.4 Notion：最近、收藏与个人任务的不同作用

**官方事实：** 当前 Home 导航按 Recents、Favorites、Teamspaces 等组织，My Tasks 与 Library 有持续可达的入口；Inbox 汇总通知。[Notion 当前导航说明](https://www.notion.com/help/navigate-with-the-sidebar)

**对 Plotstay 的判断：** 支持将“常去哪里”“有哪些任务”和“有什么更新”分开表达。当前不需要学习它的完整可配置侧栏或更多内容入口。旧版 Notion Home 的图不能当作当前版本逐像素参考。

### 3.5 Shopify：业务任务与可关闭卡片不同

**官方事实：** 首页把未完成订单动作按类型汇总并显示数量；一般首页卡片可以关闭，订单任务卡例外。[Shopify Home](https://help.shopify.com/en/manual/shopify-admin/shopify-home)

**对 Plotstay 的判断：** 可借鉴审核任务汇总和不同重要性事项的处理方式。回复评价属于自愿互动，其提醒不宜与审核责任、阻碍继续提交的问题表现得同样强制；具体如何区分见下方待讨论建议。销售分析与商业建议不属于本轮 Plotstay 首页目标。

### 3.6 Contentful：任务归属与完成后退出

**官方事实：** 内容任务关联具体条目，可指派给个人或团队，并有本人待办列表；组织的 Spaces 页面也有完成后移除的 Open tasks。[内容任务](https://www.contentful.com/help/content-and-entries/tasks/)、[Spaces 页面](https://www.contentful.com/help/spaces/)

**证据边界：** Spaces 中的 Open tasks 涉及空间许可、续约等管理动作，不是内容编辑首页。本调研只用它说明任务完成后退出及按角色显示的模式，不把它描述成与 Plotstay 相同的创作工作台。

**对 Plotstay 的判断：** 个人待办需要任务对象、责任关系、当前状态和结束条件。仅显示一条活动记录或提供一个链接，还不足以保证它是真正的待办。

## 4. 可采用的通用原则

NN/g 的复杂应用指南强调状态可见、用用户熟悉的概念、让用户识别而非回忆、保持控件语义一致，以及减少无关信息。应用到 Plotstay：在行内讲清主体和世界；状态变化有反馈；同一种操作使用一致名称和图标；首页只显示任务摘要。[复杂应用可用性指南](https://www.nngroup.com/articles/usability-heuristics-complex-applications/)

空状态需要解释系统状态并给出有用的起点，还必须区分真正没有记录、尚在加载和加载失败。它不要求每个可选栏目都保留一个大空框。[空状态指南](https://www.nngroup.com/articles/empty-state-interface-design/)

因此，隐藏无记录的常用世界、同时在快捷开始保留未来的浏览入口，是合理的情境选择；不能把加载失败当成“没有常用世界”静默隐藏。

## 5. 与已确认方案逐项对照

| 已确认选择 | 复核结论 | 仍需注意 |
| --- | --- | --- |
| 需要你处理必须有具体动作 | 有直接产品依据 | 点击并不等于完成；动作还要有权限与结束条件 |
| 继续处理仅收录本人未完成工作 | 合理，支持个人聚焦 | “本人”如何识别须可靠，尤其管理员代编和历史手记 |
| 角色／项目／世界／互动分组 | 适合现有对象模型 | 四分法是本项目选择，具体名称和理解成本需测试 |
| 分组＋主体＋信息 | 符合识别、状态可见等原则 | 简洁层级即可，不必给每条内容造一张大卡片 |
| 互动随状态分入不同栏目 | 有评论草稿与通知分离的参考 | 可选回复如何退出待办、历史事件如何标时需补齐 |
| 常用世界＋未来所有世界 | 有很近的空间导航案例 | 固定、最近访问和管理权限须分别表达 |
| 没有常用记录时隐藏栏目 | 可以保留 | 新用户仍有起点；加载和错误不可伪装为空 |
| 每组少量摘要＋查看全部 | 合理 | 首页条数不是事项总数，跨世界顺序需要稳定 |

## 6. 新发现、建议与确认状态

### R-01：可选回复与处理责任分层

**最新决定：** 审核、退回修改排在前面；未回复评价留在同一栏目并标明“可回复”。用户明确将“暂不回复／收起提醒”放到远期优化，本轮不实现。下方收起机制为远期参考。

**问题：** “有动作可以做”范围很宽。一条评价可以回复，不代表用户必须回复；若所有未回复评价长期算待办，数量会越积越多。

**建议：** 保留在“需要你处理”内，但将审核／退回修改与“可回复的评价”分层，后者显示“可选回复”，考虑允许“暂不回复／收起此提醒”。提醒的收起不能删除评价或改变业务审核状态，未来新评价是否重新提示需明确。

**取舍：** 增加一点状态管理，但可减少无意义的待办压力。不建议为了清零让用户执行虚假的完成动作。是否移动到独立互动栏也是可讨论替代，当前优先考虑保留已确认布局。

### R-02：按动作与版本去重，不按整个对象去重

**最新决定：** 用户已确认，已同步首页收录与验收规则。

**问题：** 同一个项目可能有公开版、新草稿、待审版，以及另一个待回复评价。仅用一个“草稿／已审核”标签，或规定整个项目只能出现一次，会丢失真实事项。

**建议：** 将“同一当前工作不重复”明确到具体动作与版本／发言。例如“星港旅舍：公开版仍在线，新的入住说明尚未提交”；另一个评价的回复任务可以独立出现。进入详情后定位相应版本，不能因阅读提醒就清除待办。

**边界：** 沿用现有服务端允许的版本并存规则，不在首页讨论中新增在审编辑能力。

### R-03：个人继续工作需要来源说明

**最新讨论：** 用户认可可信依据的必要性，并提出两个选项卡切换。建议在“继续处理”内部区分“我的创作／我协助编辑的”；范围、共享世界配置的归类和页签显隐尚未确认。页签不能代替服务端归属与权限判断。

**问题：** 作者身份、管理权限、最后编辑者、最近浏览者是不同关系。只按作者筛选会漏掉管理员真正进行中的代编；只按管理权限筛选会继续混乱；最近浏览也不能证明有工作未完成。

**建议：** 实现前先核对已有创作和版本记录能否证明“本人创建／本人保存的未完成修改”。数据不足时宁可显示较少且可信的记录；不按角色绑定推断所有权，也不为了首页引入整套任务分配系统。审核队列继续按审核能力独立展示。

### R-04：常用世界兼顾稳定与最近访问

**建议：** 固定项顺序保持稳定；自动补充项标为“最近访问”，与固定项去重。进入世界与进入管理使用两个明确目的地。既能管理又能浏览的用户不应猜测点击世界名会去哪里。

**尚未定：** 固定入口、取消固定、数据存储／跨设备和访问记录范围。此处是对已确认常用世界方向的细化，不是新增收藏平台功能的授权。

### R-05：快捷开始中的“＋”应与创建动作一致

**最新决定：** 用户同意加号只用于创建，管理入口使用普通导航样式；已同步首页方案。

**问题：** 当前“＋ 创建或管理角色”和“＋ 管理世界内容”会进入管理页面，加号容易让人预期直接创建。

**建议：** 保留快捷开始栏目；去管理列表使用普通导航入口，真正创建才用加号。后续可以区分“创建角色”和“管理角色”，但应以能力和实际目标路由为准。

这是控件预期与动作匹配的问题，不能完全留到最后只改文案。创建和管理是否拆成两个独立入口仍随具体布局细化。

### R-06：保持浅层结构，用紧凑列表控制密度

**建议：** 继续处理采用组标题＋两三行摘要的紧凑条目，名称醒目、世界和状态次级展示。避免每个类型、世界、角色都继续嵌套一层；将来多世界任务量上升时，优先考虑局部筛选而非深层树。是否需要筛选用真实任务量验证，不立即增加。

小屏优先保留对象、说明和动作；发布时间与编辑时间采用明确标签，不能都写成含义不清的“最近”。

## 7. 用什么验证，而不是仅凭案例下结论

建议下一步做带数据的静态或交互原型，对以下场景开展小规模任务测试。本轮未执行这些测试，也没有任务成功率数据。

| 场景 | 用户任务 | 观察点 |
| --- | --- | --- |
| 新用户，无世界记录 | 找到创建角色或浏览世界的起点 | 没有空栏目也能理解下一步 |
| 多角色、多项目作者 | 找到昨天没写完的指定草稿 | 是否需要读完所有卡片，主体能否区分 |
| 多世界管理员 | 找到有权审核的事项并识别其世界 | 全站数据是否挤占个人工作，是否误进他人草稿 |
| 提供者收到多条评价 | 回复其中一条，其余保留“可回复”状态 | 是否误认为必须全部回复；收起提醒测试留远期 |
| 已公开项目继续修改 | 判断公众现在看到什么、自己接下来编辑什么 | 能否理解公开版与新草稿并存 |
| 手机、长名称、部分请求失败 | 找到目标并继续处理 | 操作是否可见，失败是否误报为空 |

记录任务完成情况、误点、寻找时间、需要解释的词，以及从详情返回能否继续原工作。不预先宣称“四分组一定比其他方案快”，也不把其他产品的采用率当成本站体验数据。

## 8. 推荐后续顺序

1. 继续逐页讨论，首页整体架构保留。
2. R-01、R-02 和 R-05 已形成上述决定；继续讨论 R-03 的两个范围页签，其余作为实现细化与视觉参考。
3. 页面规则相对稳定后，用同一批示例制作桌面与手机稿，再验证空状态和多人多世界情景。
4. 再进入已授权的实现、测试与开发站部署；本次没有修改代码、数据库或线上服务。

调研不要求替换框架、引入 CMS、复制完整 Asana／Notion 自定义系统，也不调整第二阶段既定的资格、审核与存档规则。
