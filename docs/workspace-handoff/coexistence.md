# 新旧后台并存与人工迁移验收

依据：2026-10-12 用户体验草图后认可整体设计与交互，指出返回按钮和面包屑不足；明确要求开发时保留旧方案，先让两套后台并存，人工体验后再决定还有哪些内容需要迁移及如何迁移。世界管理尤其需要逐项评估。

**这是实施约束，不是尚待确认的选项。整体认可不表示世界管理所有模块已经定稿，也不授权启动应用实现或删除旧版。**

## 1. 入口与切换

- 保留现有 `/{locale}/account`、`/{locale}/admin` 及原 query/deep link，继续进入旧版，不强制重定向新版。
- 新版采用独立私有入口，建议 `/{locale}/workspace`，其内部仍可用 view／实体 ID 等参数组织。最终路径由 WS-00 冻结；不改公开页面、前台菜单或既有 URL 行为。
- 仅在后台加入“试用新版后台／返回旧版后台”入口。切换时尽量带上当前世界、作品、语言和列表上下文；新版尚无对应功能时回旧版对应工具，不让用户从菜单重找。
- 切换前处理未保存修改：明确保存／放弃／留在当前页；不能只切 URL 丢输入。返回目标只能是允许的同站后台路径，不信任任意 returnTo URL。
- 新入口同样受应用鉴权、Basic Auth、noindex、no-store 和 robots 规则保护。隐藏入口不是鉴权。

## 2. 同一份业务数据，兼容两套客户端

共享账号、世界、内容、版本、审核和权限，不复制出第二套内容库；在新版保存并刷新旧版，应看到同一已保存版本。旧版保存后新版也能读到；同时打开旧／新编辑器时仍做版本冲突检查，不互相静默覆盖。

保留旧界面不代表冻结旧业务漏洞。BUG-001 的申请替代、BUG-002 的稳定双语项目，以及第二阶段入驻／世界公开门槛，必须在公共 domain 层生效。旧页面不能因仍走原 API 而绕过新规则。

WS-00／03／08 需说明旧客户端兼容方式：新增字段在旧版保存时不丢失；稳定项目 ID 与顺序可往返；旧客户端不认识的新类型明确转到新版或拒绝该操作并解释，不能把未知字段覆盖为空。优先做最小兼容适配；若确有不能双向编辑的对象，必须逐项说明并在交接中标为限制，不能笼统称为“两套都可用”。

并存期间原工具保持可达，角色审核、导入、翻译任务、共享资料、提供者绑定、下架及历史恢复照常受到原有或新确认的服务端限制。回退到旧界面只改变交互入口，不回滚已保存数据，不撤销迁移或放宽权限。

## 3. 世界管理的逐项人工清单

初始状态全部为“待核对／旧版保留”。表格中的新位置是候选，不表示最终结构已经获批。工程师实施后补充准确旧入口、新入口、截图或操作记录、用户体验结果及遗留问题。

| 操作组 | 新版候选位置 | 用户体验时重点看 | 当前迁移状态 |
| --- | --- | --- | --- |
| 世界首页配置、栏目及推荐内容 | 世界设定 → 首页 | 能否找到现有全部配置、看清影响范围及保存发布状态 | 待核对；旧版保留 |
| 地点资料 | 世界设定 → 地点 | 列表／详情／引用作品来回是否顺畅，共享影响是否清楚 | 待核对；旧版保留 |
| 共享人物／文案 | 共享资料及引用入口 | 谁能改、影响哪里、预览用哪件作品、历史如何恢复 | 待核对；旧版保留 |
| 世界作品列表及三类编辑 | 世界内容 | 筛选、编辑、返回定位、字段完整性是否优于旧版 | 待核对；旧版保留 |
| 作品审核、下架、恢复、站点限制 | 审核与历史详情 | 正在操作哪个版本、为何受限、退回后怎么继续 | 待核对；旧版保留 |
| 评价／提供者回复审核与绑定 | 世界审核／作品经营角色 | persona 与编辑资格是否容易区分，旧动作是否完整 | 待核对；旧版保留 |
| 批量导入、预演、翻译与失败重试 | 管理工具 | 复杂操作是否值得重排，是否只需更好入口和返回 | 待核对；旧版保留 |
| 管理成员与权限 | 成员 | 管理角色范围清楚，不与入驻资格混淆 | 待核对；旧版保留 |
| 入驻申请、邀请及资格取消 | 入驻管理 | 新增流程；取消资格与下架分离，返回申请队列保留位置 | 第二阶段新增，待确认细则 |
| 创建世界、首次公开审核 | 世界进度／网站审核 | 新增流程；草稿世界内容预览及未公开原因清楚 | 第二阶段新增，待确认细则 |

建议迁移状态依次记录为：`旧版保留／待核对 → 新版可试用 → 用户要求调整或补项 → 用户确认可替代`。尚未迁移的工具可继续由旧版承接，不能为了让表格全绿而草率重做。

## 4. 技术验收与用户体验分开

技术验收包括：双向读写及字段保留、旧新同时编辑的冲突、权限一致、旧入口可达、数据和历史不变、前台一致、认证及禁止索引。

人工体验由用户在同一账号和世界内分别执行任务，记录是否找得到、是否能返回原上下文、信息是否足够、哪些旧功能遗漏、哪些迁移方式需要调整。世界管理可以按上表分批体验，无须一次决定全部模块。

**WS-07／WS-13 的“交付”意味着可以并存试用，不意味着旧版退役。** 用户明确确认相应功能已完整迁移，并另外同意停用旧版后，才能另建退役任务。删除旧页面／API、强制切换、改变默认入口，不随此次任务自动执行；没有固定退役日期。

## 5. 对现有任务的补充门槛

| 任务 | 追加交付／验收 |
| --- | --- |
| WS-00 | 双入口路由表、旧 API 兼容矩阵、世界管理逐项清单、返回上下文约定 |
| WS-01 | 新版独立入口和双向切换；所有层级页面有返回及可点击面包屑；旧入口不重定向 |
| WS-02／03 | 原角色／共享资料入口也遵守修复规则；旧新字段往返不丢项目 ID、顺序及未知数据 |
| WS-04／05 | 来自个人列表或世界列表，返回到正确来源；切换前保留输入；发言与版本两端一致 |
| WS-06 | 世界管理按操作组试用；旧工具继续可达，用户未确认的布局不视为最终迁移 |
| WS-07 | 发布可并存试用版本，交付人工体验清单；不删除或重定向旧后台 |
| WS-08／09／10／12 | 新业务门槛覆盖旧 API；迁移兼容旧客户端，明确不支持对象和处理方式 |
| WS-11／13 | 新增流程可试用；跨界面上下文与真实版本一致；保留未退役旧功能 |

这份补充优先于此前“旧链接分流至新页面”等迁移描述；旧功能去向表仍作为新版位置提案使用。
