# 工作台首页体验调整方案

记录日期：2026-10-12。页面：`/zh/workspace`、`/en/workspace` 的概览。

**状态：用户已确认下述产品方向，本轮仅记录详细方案，尚未实现。** 用户希望继续逐页讨论修改；记录本方案不代表启动页面开发或第二阶段 WS-08～13。后续讨论继续补充对应页面文档。

调整前归档基线为 `dbcbcc6`，已提交并推送，包含第一阶段收口和第二阶段规则；运行时代码仍为 `8d66a07` 的实现。本方案补充 [页面与交互规格](design-spec.md)，首页规则有差异时以本文件为准。第二阶段权限与存档仍遵循 [已确认规则](decisions-pending.md)。

## 1. 用户反馈与目标

后续 [参考调研与设计复核](overview-research-2026-10-12.md) 提供官方案例和 R-01～06 建议。用户随后确认：审核／退回修改优先，可选回复标明“可回复”；暂不回复／收起提醒留远期；按具体动作与版本去重；个人工作须有可信依据；加号只用于创建。下文已同步。用户提出通过两个选项卡区分个人与协助编辑，具体范围和呈现仍在讨论；R-04、R-06 的新增细节尚未确认。

- “需要你处理”缺少可见示例，用户无法理解会出现哪些内容；每条信息必须对应一个当前可执行的动作，点击即可去完成。
- “继续处理”混合角色、服务等对象，缺少组织；需要同时看清 **分组、主体、信息**。
- 用户认可世界名、内容类型、审核状态以及“角色草稿已保存，尚未提交”这类说明，要求通过 UI 层级讲清各自含义。
- 管理员能访问的全部内容，不因此变成管理员自己的未完成事项。
- 保留“快捷开始”和“最近的进展”；在快捷开始上方增加常用世界入口。
- 没有常用世界记录时隐藏整栏。未来增加左侧“所有世界”，并通过轻量提示引导新用户浏览。
- 本轮先对齐功能、信息架构与状态，栏目名、提示语、中英术语和具体视觉样式后续统一调整。

## 2. 当前实现盘点

依据基线源码 [workspace.ts](../../apps/web/src/lib/workspace.ts)、[workspace.astro](../../apps/web/src/pages/[locale]/workspace.astro) 与 [persona-reviews.ts](../../packages/domain/src/persona-reviews.ts)。以下是现状，不是目标验收标准。

| 栏目 | 当前实际行为 | 与目标的差距 |
| --- | --- | --- |
| 需要你处理 | 展示部分角色退回、本人评价退回、提供者收到的评价，以及各世界已送审内容汇总 | 提供者评价没有排除已回复项；未完整区分回复草稿、待审和退回；首页审核入口还需按具体审核能力筛选 |
| 继续处理 | 拼入部分角色草稿、评价草稿和每个可管理世界的前两条内容 | 世界内容没有按本人未完成事项筛选，可能出现已完成内容；没有分组；主体与归属层级不清 |
| 最近的进展 | 目前主要填入已批准角色，空时显示“审核和发布状态会显示在这里” | 尚不是完整的审核、发布及互动进展汇总 |
| 常用世界 | 无此栏目 | 需要设计访问记录、固定入口及权限处理 |

现有实现还会先截取部分列表再判断状态，世界内容按异步返回顺序追加。后续实现应先确定符合条件的事项，再稳定排序和限量；不能把取到的少量记录当作完整待办总数。

## 4. 需要你处理

### 收录规则

每条事项均须回答：**哪个对象、发生了什么、当前用户可以做什么。** 用户现在有权完成一个明确动作时才进入此栏。仅等待别人处理的状态放进“最近的进展”。

| 事项 | 主体和上下文 | 主要动作 |
| --- | --- | --- |
| 本人角色资料退回 | 角色名称、退回说明 | 查看意见并修改 |
| 本人项目版本退回 | 项目名称、世界、类型、退回说明 | 查看意见并修改 |
| 本人评价或回复退回 | 发言主体、关联项目、世界、署名角色 | 查看意见并修改 |
| 提供者收到尚未回复的评价 | 关联项目、世界、可用的提供者角色及评价摘要 | 查看并回复 |
| 当前用户有权处理的审核事项 | 世界或具体对象、审核类型、数量或摘要 | 进入对应审核队列或详情 |

本人项目、世界送审、入驻等事项按对应功能实际开放情况接入；这张表不授予普通账号尚未上线的编辑权限。

### 行为要求

- 点击名称或主要操作，直接进入对应对象、意见或带筛选的队列；避免跳到通用列表后再次手动寻找。
- 审核、退回修改排在前面。未回复评价继续放在同一栏目，标明“可回复”，降低催促感，不引入强制回复规则。
- “暂不回复／收起提醒”明确留作远期优化，本轮不实现，也不以此作为当前验收门槛；今后接入时只处理提醒，不删除评价。
- 已回复、已提交等待审核的回复，不继续显示“去回复”。已有回复草稿时归入“继续处理 → 互动”。
- 管理员审核任务按真实审核能力生成；只有编辑权限者不能收到“去审核”。管理身份不授予替别人发言的能力。
- 完成动作后重新核对状态，移出或转入对应栏目；服务端仍逐请求检查权限与当前版本。
- 计数只统计真实事项，加载提示和错误提示不计入。若按世界汇总，界面须区分“几项任务”和“几条待审核内容”。

## 5. 继续处理

### 分组及个人范围

| 分组 | 收录对象 | 需要显示的归属 |
| --- | --- | --- |
| 角色 | 自己尚未完成、尚未提交的角色资料草稿 | 角色名称；角色资料本身没有世界归属时不硬填世界 |
| 项目 | 住宿、体验／活动、服务的未完成草稿或尚未发布的修改 | 项目名称、世界、类型；有意义时显示经营角色 |
| 世界 | 自己正在处理的世界设定、首页配置等未完成修改 | 世界名称、具体修改模块 |
| 互动 | 自己尚未提交的评价草稿、提供者回复草稿 | 发言标题或明确动作主体、关联项目、世界、署名角色 |

- 首页只展开“分组 → 具体事项”两层；不增加多层分类树。
- 重点展示本人创作或本人正在继续的工作。不能仅凭账号拥有管理权限，把整个世界的草稿填入个人栏目。
- 管理员实际保存的未完成代编修改需要考虑纳入。依据本人创作归属、创建／保存记录核对，不能只按作者筛选，也不能只按管理权限筛选；打开／浏览过内容不等于产生编辑任务，角色绑定不证明作品所有权。具体数据契约在实现前细化，不引入整套任务分配系统。
- 已完成且没有后续动作的内容不进入此栏。“已审核”本身不足以判断是否完成：若确实仍需当前用户发布，应写明具体待完成动作，并按权限处理。
- 每组默认显示最近修改的 2～3 条，提供“查看全部”；空组隐藏。具体上限在视觉稿中选定。
- “其他”暂不设置，现有评价和回复归入“互动”。后续新功能出现时再判断其归属。

### 分组、主体、信息的 UI 层级

**选项卡提案（讨论中，尚未确认）：** 用户提出用两个选项卡区分工作范围。建议只在“继续处理”内部使用“我的创作／我协助编辑的”：前者展示本人创作归属下的未完成事项，后者展示有权限且有本人实际保存记录的代编事项。同一工作不跨两页签重复；页签内部沿用实体分组并隐藏空组，不增加全站身份切换。世界共享配置等不具备单一作者归属的对象如何分配、页签显隐与计数尚待确认，不能仅凭角色名称或创建事件推断归属。

| 层级 | 显示内容 | 要求 |
| --- | --- | --- |
| 分组 | 角色／项目／世界／互动 | 使用独立组标题，避免与单条内容类型混淆 |
| 主体 | 具体角色、项目、世界或发言名称 | 单条中最醒目；不能只显示一句状态说明 |
| 归属 | 世界、关联项目、署名角色等 | 明确关系，可用路径或带标签字段；不把全部信息拼成含义不明的一行 |
| 类型与状态 | 住宿／服务／评价，以及草稿／退回等 | 视觉上与名称、说明分开，状态不能只靠颜色表达 |
| 说明 | 如“角色草稿已保存，尚未提交” | 保留具体、有用的完整句子 |
| 操作 | 继续编辑、查看意见、继续回复等 | 动词说明下一步，避免统一用“打开内容” |

用户给出的现状示例为：`Live acceptance review service / 拉斯世界 · 手记 · 已审核 / 打开内容`。调整时先判断该条是否还有本人待完成动作，再决定是否收录；标题中的英文单词不能用来推断真实内容类型。若收录，须明确手记主体、关联项目与世界，类型和状态分别展示。

后台手记与角色评价存在来源差异；不能仅凭 `review` 类型就把所有管理手记当成本人互动。历史手记的个人任务归属需结合作者、来源及实际操作核对，沿用原权限和来源语义。

## 6. 评价、留言与回复在首页的归属

本次使用现有评价和提供者回复能力；“留言／评价／手记”等对外用词后续统一，不自动扩展多轮讨论系统。

| 当前情况 | 首页栏目 | 下一步 |
| --- | --- | --- |
| 收到评价、尚未回复且当前用户可回复 | 需要你处理 | 查看并回复 |
| 本人评价或回复被退回、尚未开始新修改 | 需要你处理 | 查看意见并修改 |
| 本人评价或回复已保存未提交草稿 | 继续处理 → 互动 | 继续编辑或回复 |
| 已提交、等待审核 | 最近的进展 | 查看提交状态 |
| 审核通过或发布完成 | 最近的进展 | 查看结果 |
| 自己的评价收到提供者回复 | 最近的进展 | 查看回复 |

按具体动作及其关联版本／发言去重，同一件当前工作在“需要你处理”和“继续处理”之间避免重复，不能按整个项目去重。例：收到评价 → 保存回复草稿 → 提交回复，依次归入“需要你处理 → 继续处理／互动 → 最近的进展”。退回后先提示看意见，保存新的修改草稿后转入继续处理。

同一项目的内容修改和另一条评价回复是不同工作，可以分别出现。已公开版本与新修改状态同时讲清，例如“已公开 · 有未提交修改”；进入后定位相应对象／版本。仅阅读或点击提醒不视为完成，沿用服务端已有版本并存与送审规则。

“最近的进展”可以保留历史事件，但应标明发生时间与当时状态，不能让过往退回事件看起来仍是当前未处理任务。事件保留时长和条数尚待细化。当前没有完整未读模型，不标注虚假的未读数量或新消息红点。

## 7. 常用世界与未来的所有世界

### 常用世界

- 放在右侧“快捷开始”上方，名称暂用“常用世界”，最终文案待统一。
- 支持用户固定常用世界，其余位置补最近访问的世界，总共显示 3～5 个；固定项与最近项合并去重。
- 每项显示世界名称，按真实关系显示管理者／创作者等身份；仅访问过时不推断已入驻。
- 提供明确的“进入世界”；有管理权限时另附“管理”入口，两个目的地须可区分。
- 没有记录时隐藏整个栏目，不放占位世界或空面板。
- 常用、固定、最近访问均不授予世界可见性或管理权限；不显示已无权访问的私有世界。

### 新用户与所有世界

- 未来左侧增加“所有世界”，用于浏览用户可访问的世界；与“我管理的世界”分开。
- 没有常用记录的新用户，在现有“快捷开始”中提供轻量入口，例如“你还没有常去的世界，去逛逛吧 →”。这句话为示意文案。
- 上述入口在“所有世界”真实可用后接入；目的页面未完成时不放无效按钮。
- “所有世界”的具体浏览范围、列表结构、世界目的页面在后续逐页讨论中确认，不由首页方案自动启动前台改版。
- 最近访问如何记录、是否跨设备同步、固定顺序如何维护尚未确定；实现时需要明确，但不影响当前已确认的栏目位置与空状态规则。

## 8. 快捷开始与最近的进展

“快捷开始”保留当前创建或管理角色、管理世界内容、查看可管理世界三个方向。按真实能力提供入口；未来增加上节的新用户浏览提示。

已确认“＋”只用于真正的创建动作；进入管理列表使用普通导航样式。是否将角色创建与管理拆成两个独立入口，按后续具体布局及实际路由细化。

“最近的进展”保留，目标是汇总与本人相关的送审、审核、发布状态及收到的回复。应显示主体和时间，遵循同一套归属信息层级。用户认可该栏目不等于当前实现已覆盖这些事件。

## 10. 实施约束与待细化内容

### 约束

- 本轮仅文档，无代码修改、构建、服务重启、数据库写入或迁移；线上保持原样。第一阶段已收口，后续体验改进另行实施；旧后台继续并存。
- 页面接入真实能力与真实状态，普通作者、入驻和世界送审依赖第二阶段。跨阶段功能不以首页按钮提前开放。
- 保留前次菜单加载优化。避免为了首页分组重新逐世界拉取完整列表或增加串行等待；实现时设计有限摘要与稳定排序，独立栏目失败应可恢复。
- 中英功能和信息结构一致，正式文案后续统一；长名称与手机换行不能依靠全局裁切隐藏问题。
- 保持 Basic Auth、noindex、no-store、现有数据库和提交历史；权限以服务端为准。

### 后续细化，不作为已确认实现方案

1. 管理员“本人正在处理”的可靠判定依据，以及旧手记、代建内容如何纳入个人任务。
2. 首页摘要的数据契约、完整状态映射、排序、计数方式及每组最终展示上限。
3. 远期优化：暂不回复／收起提醒及其保留方式，本轮不实现。
4. 常用世界的记录与固定机制、存储范围、无效世界处理和最终展示上限。
5. 所有世界页面、进入世界目的地、手机栏目顺序，以及最近进展保留范围。
6. 最终中英文案、术语、视觉稿及具体对象直达和返回的路由细节。

## 11. 后续实现验收清单

- [ ] 每条待办有主体、原因和当前可执行动作；进入后定位对应对象或队列。
- [ ] 审核、退回修改排在前面；未回复评价标为“可回复”，不要求用户全部回复；不以远期收起提醒能力作为本轮验收条件。
- [ ] 已回复评价不再显示“去回复”；回复草稿、待审、退回按状态进入正确栏目。
- [ ] 管理员不会因管理权限而看到全世界草稿充当个人未完成事项；编辑者不出现无权使用的审核操作。
- [ ] 继续处理按角色、项目、世界、互动分组，空组隐藏，组内排序稳定，有可用的查看全部入口。
- [ ] 世界、项目、角色和发言主体关系可辨认；名称、类型、状态与说明有明确层次。
- [ ] 已完成且无后续动作的内容不进入继续处理；已审核未发布的条目按真实后续动作判断。
- [ ] 保存草稿、提交、退回、重改及完成后正确转栏；同一动作／版本不在两个操作栏目重复，同一项目的不同动作不被误删；公开版与新修改状态可辨认。
- [ ] 快捷开始中的加号只对应实际创建动作，管理列表使用导航入口。
- [ ] 常用世界有记录才显示，固定与最近项去重；无记录时整栏隐藏。
- [ ] 所有世界可用后，新用户在快捷开始看到浏览提示；可访问世界与可管理世界范围分开。
- [ ] 最近进展展示真实主体、时间和状态，没有虚构未读提示。
- [ ] 中英、手机、长标题、空状态、部分加载失败及权限变化可用，加载体验没有明显倒退。
- [ ] 用明确标注的示例完成视觉验收，再验证真实接口与状态；不污染现用数据库。

以上为未来验收要求，本次未执行应用测试或宣称页面已通过上述验收。

## 12. 视觉与交互设计依据

用户补充要求：后续修改须尽可能参考竞品或遵循产品理念，字号、尺寸与交互需要专门对齐。功能方案确认不等于视觉验收完成。以下为后续出稿和实现的工作依据；具体数值与效果在界面稿中核对，不冒充已批准的视觉成品。

### 产品原则与参考分工

首页帮助用户看清“我在处理什么、属于哪里、下一步做什么”。主体清楚、任务可信、操作可达、反馈及时，以及中英和手机的一致可用性，作为设计判断依据。

| 设计方面 | 参考依据 | Plotstay 的应用方向 |
| --- | --- | --- |
| 首页栏目与个人工作范围 | 调研中的 Asana | 任务、继续工作、项目快捷入口各有清楚用途 |
| 单条内容信息层级 | 调研中的 Strapi | 名称、类型、状态、时间分别表达，主体优先 |
| 世界入口与目录 | 调研中的 Confluence | 常用入口和完整目录分工明确，访问与管理目标可辨 |
| 字体、色彩、边框和图标 | Plotstay 现有已认可的后台及品牌基线 | 统一组件语义；若需要调整既有风格，用前后对照明确呈现 |

参考链接及已查看官方截图见 [调研记录](overview-research-2026-10-12.md)。引用竞品时说明具体借鉴哪种行为或层级；各产品的布局、颜色和尺寸不直接拼接成本站设计规范。

### 后续需交付的视觉规格

- **文字层级：** 页面标题、栏目标题、分组标题、主体名称、正文说明、辅助信息与状态标签分别规定字号、字重、行高和颜色；主体应先于辅助信息被识别。正式数值结合现有字体及中英实稿选定。
- **尺寸与密度：** 统一栏目间距、行内间距、内容内边距、按钮尺寸和页签高度。用少量／多量数据验证页面长度；不能只根据空页面决定尺寸。
- **状态表达：** 状态色结合文字标签；审核、退回修改和“可回复”的强度有区分；公开状态与新修改状态不能挤成一个含义不明的标签。
- **交互反馈：** 页签的默认、选中、悬停、键盘焦点与切换状态明确；主体链接和主操作目的地一致或清楚区分；执行后给出结果并更新当前事项，返回保留合理上下文。
- **可读与可操作：** 关键归属信息不因次级样式而过小或过淡；长标题可换行；手机操作区易点按；不把必要操作仅放在悬停态。
- **加载与异常：** 页面导航在数据请求期间可使用；各栏目提供符合实际的加载、无数据、失败与重试状态，避免请求先后顺序造成内容反复跳动。

### 界面稿与验收安排（建议流程）

1. 逐页功能讨论继续进行，同时积累共用组件规则。
2. 先以首页制作带明确示例数据的界面稿，展示桌面／手机、中英，以及普通作者／有协助编辑任务的管理者。按两个范围页签的提案出稿，具体名称和共享配置归属仍需核对。
3. 展示无数据、少量数据、多世界长列表、长名称及失败状态；交互稿演示页签切换、进入对象、返回与动作完成反馈。参考图旁注明借鉴点，方便用户比较。
4. 将选定的字号、间距、按钮、标签、页签等记录为可复用规范，供后续页面沿用；按实现授权接入真实数据，再用实际浏览器截图对照。

本次只记录上述要求与建议流程，未制作新界面稿或修改线上样式。不因加入视觉验收而重复确认已经明确的权限、提交存档与任务规则。
