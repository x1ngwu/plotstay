## 本轮开发范围与前台保护

这里的“后台”包括普通用户工作台、世界管理工作区、网站管理员界面，以及支持这些任务所需的接口、权限、审核、版本与必要增量数据结构。普通用户的 `/account` 属于本次后台范围，不能因为它面向普通用户就误归为前台。

| 范围 | 实施约束 |
| --- | --- |
| 用户工作台与管理界面 | 可以调整导航、排版、表单、状态反馈与操作流程；按本方案分步补齐功能 |
| 后台可视化编辑与受保护预览 | 复用现有前台页面效果作为预览基准，编辑控件、选区、高亮与面板只存在于后台编辑环境 |
| 支持后台的后端能力 | 可以补齐入驻、世界审核、作品授权等能力，兼容现有公开页面的数据读取与渲染契约 |
| 现有前台 | 保持首页、搜索／列表、住宿／活动／服务详情、评价展示、预订与凭条页面的排版、样式、文案和已有交互；语言、字体、主题、导航和 URL 行为保持现状 |
| 新的公开页面或交互 | persona 公开主页、多轮对话界面、公开入驻入口或世界介绍页等不随后台重构上线；本方案只保留已讨论的扩展方向 |

前台现有入口继续可用，新增申请、创建世界等任务先在工作台内组织。不能为接入编辑器顺带改版公开页面、调整前台菜单或添加面向游客的编辑按钮。案例中的模板切换、配色与样式设置只是研究材料，不表示授权改动 Plotstay 前台视觉。

优先将后台样式和交互限定在后台布局与组件内。必要时可对共用代码做保持公开输出和行为不变的整理；不能通过全局样式、共用布局或编辑器依赖影响前台。若候选工具要求重写公开页面模板或改变前台体验，应记录为选型不符合当前范围的问题，不默认扩大本轮任务。

“前台保持现状”指呈现与既有使用体验保持现状。用户日后通过正常后台编辑、审核、发布更新内容，前台仍按原有模板展示相应已发布数据；草稿和待审版本不泄露。此次重构与验证本身不批量改写既有文案、发布内容或历史凭条。

## 新旧后台并存与返回导航（用户已确认）

开发期间保留旧后台完整入口和可用功能，新版独立提供试用入口；用户人工体验后再决定尚需迁移哪些内容及如何迁移，尤其世界管理不能以当前草图视为全部定稿。共享现有数据和业务规则，不建立第二套内容库；新权限和审核规则也必须作用于旧接口。

所有层级页面补齐返回按钮和可点击面包屑，世界设置及内容编辑可回原上下文，不要求从菜单重走。正式实现保留筛选和位置、统一保护未保存输入。旧版在用户明确确认迁移并同意停用前，不删除、不强制跳转、不以自动测试通过代替人工迁移验收。

具体双入口、客户端兼容、世界管理逐项体验表和任务补充门槛见[并存方案](workspace-handoff/coexistence.md)。原方案阶段只修订文档与草图；第一阶段实现及尚待体验的路径见[实施记录](workspace-handoff/phase-one-implementation.md)。

## 用户任务与身份关系

已确认四类主要任务：

1. 拥有或参与管理世界，维护世界并处理入驻申请与内容审核。
2. 以 persona 作为经营者，创作住宿、活动、服务，编辑页面内容并处理收到的评价。
3. 以 persona 作为游客，发表和修改评价，查看回复；预留未来多轮对话能力。
4. 创建和修改 persona 的名字、头像与简介，预留未来公开角色主页。

账号承担所有权与操作权限，persona 承担故事内署名。同一 persona 可以作为房东、向导、服务提供者或游客，也可跨世界使用。进入工作台默认查看整个账号的内容，支持按角色与世界筛选；实际创作或发言时明确展示本次身份。

作品编辑授权与经营者 persona 绑定分别管理。拥有某 persona、获得入驻资格、成为世界管理员分别表示不同能力，不能互相推导。普通创作者只管理自己的作品；明确的作品协作授权留待需要时设计，不通过入驻资格授予全世界内容编辑权。

## 入驻与作品权限

已确认规则：

- 入驻资格属于“账号＋世界”。申请可以说明创作方向和拟使用角色；通过后使用该账号的不同 persona 不需要分别申请入驻。
- 入驻前可以创建、保存和私有预览本人在目标世界的住宿、活动、服务草稿；获批后才能送审。一次入驻覆盖三类作品，具体作品分别接受内容审核。草稿准备不扩大私有世界读取权限。
- 世界提供“开放申请”和“仅限邀请”两种方式。邀请接受等细节留实施设计，不据此开放公众注册。
- 入驻审核决定是否允许该账号在本世界送审作品及开展相应经营操作；内容审核决定具体版本是否可以公开。保存草稿与正式送审分别授权。
- 取消入驻资格后，停止新增作品、提交修改和提供者回复；已有作品与历史保留，下架由管理员另行决定。
- 资格取消后，旧稿与历史仍可读，服务端停止保存新修改；尚未完成的作品送审失效并提示“资格变更，需重新提交”，审核不能放行。恢复资格后由作者明确重提，不自动送审或发布；浏览器未保存输入可复制带走。此限制优先于入驻前可以准备草稿的规则。
- 正式提交固定当次内容／版本并形成存档，包含提交与审核记录；被拒绝也保留，修改重提不覆盖原存档。入驻申请、世界送审与作品送审均按此处理，历史查询仍需鉴权。
- 普通游客的发言资格单独管理，取消经营资格不自动等同于游客禁言。游客评价无需先入驻，沿用角色和发言审核规则。
- 普通入驻者提交作品，由世界管理员审核后发布。
- 世界所有者和有发布权限的管理员可以自行发布自己的作品，保留明确发布操作、版本与操作记录。保存草稿不会自动发布。
- 网站管理员保留全站管理与下架能力，网站施加的限制不能被世界发布操作绕过。

| 能力 | 普通用户 | 获准入驻者 | 世界所有者／有相应权限的管理员 |
| --- | --- | --- | --- |
| 管理自己的 persona、以角色写游客评价 | 可以，沿用审核规则 | 可以 | 可以，角色资料仍按网站审核边界处理 |
| 在目标世界创建和编辑自己的住宿／活动／服务草稿 | 可以，资格被取消者除外；不扩大私有世界读取权 | 可以 | 可以，按世界权限 |
| 提交自己的作品审核 | 获准入驻后才可 | 可以，发布需审核 | 按世界相应权限处理 |
| 编辑其他用户作品 | 无默认权限 | 无默认权限 | 按本世界管理权限 |
| 审核入驻和普通投稿 | 不可以 | 不可以 | 按本世界相应权限 |
| 审核世界首次公开、跨世界角色资料 | 不可以 | 不可以 | 世界权限本身不授予此能力，由网站管理员处理 |

2026-10-12 已确认入驻前草稿、取消资格后的旧稿与在审稿处理，以及提交存档规则，见[第二阶段规则](workspace-handoff/decisions-pending.md)。拒绝后重申、邀请有效期等申请／邀请契约细节仍待冻结。取消资格的限制须覆盖新旧写入、审核和恢复入口，不能被旧待审记录或“未入驻可写草稿”绕过。

## 创建世界与公开

已确认流程：**用户创建世界草稿 → 填写基本设定与入驻规则 → 提交网站管理员审核 → 审核通过，世界公开。**

- 创建者自动成为世界所有者，可以在草稿阶段准备世界内容。
- 世界公开前，其内部作品也不能公开；作品具备可发布状态不等于可以绕过世界公开门槛。
- 工作台展示草稿、待审核、已公开、退回等世界状态、审核说明和下一步操作。
- 世界公开后，世界所有者或有发布权限的管理员维护作品时，无须每次等待网站管理员审核。
- 已确认：世界名称、核心设定、对外标识等身份资料改动仍需网站审核，旧批准版继续公开；普通运营内容由世界管理者按权限处理。首次审核不强制示例作品；WS-09 需列出具体身份字段清单供审阅。

## 用户工作台信息架构

2026-10-12 首页体验细化已确认，见 [首页体验调整方案](workspace-handoff/overview-experience-spec.md)，尚未实施。概览按当前可执行待办、个人未完成工作、近期进展组织；继续处理分角色／项目／世界／互动，明确主体与归属；常用世界有记录才展示。未来“所有世界”与新用户浏览提示按该方案及后续页面讨论接入。

| 一级入口 | 主要任务 |
| --- | --- |
| 概览 | 处理退回与申请结果、继续最近编辑、查看近期互动 |
| 我的角色 | 创建与编辑 persona，查看资料审核状态，未来进入角色主页 |
| 我的作品 | 住宿／活动／服务列表，按世界与角色筛选，进入可视化编辑、预览、提交与发布 |
| 评价与回复 | 自己写的评价、作品收到的评价、收到和发出的回复 |
| 入驻与申请 | 已入驻世界、申请进度、收到的邀请与入驻说明 |
| 我管理的世界 | 创建世界、查看世界审核状态、进入具体世界管理工作区 |
| 账号设置 | 真实账号设置，与 persona 资料分开 |

“入驻的世界”与“我管理的世界”分别表达经营资格与管理权限。同一个世界可同时从两种任务入口进入。世界管理工作区再展示入驻申请、内容审核、世界设定、成员权限等工具，并提供返回个人工作台的入口。

第一阶段的原“我的作品”入口现标为“我管理的内容”：它按所选世界的既有管理权限读取住宿、活动、服务及手记。上表“我的作品”描述的是第二阶段普通作者能力的目标，不表示目前已开放本人作品列表或按经营角色筛选。

概览“需要你处理”只展示当前用户有权执行的具体动作；等待审核、通过或收到回复归入最近进展。本人未完成工作分组进入继续处理，管理权限不自动把他人草稿纳入个人任务。快捷开始保留当前可用入口；申请入驻、创建世界和所有世界随对应能力上线，常用世界空状态及新用户浏览提示按最新首页方案处理，不放无功能按钮。

通知汇总、未读状态和部分账号设置属于待补齐能力，不把概览示例视为已有实现；首批范围在任务拆分时标注。预订凭条目前使用游客浏览器身份，账号绑定和“我的旅行”不因这次布局讨论自动纳入。

## 可视化编辑方向

用户已同意“固定页面结构，编辑对应区域内容”的方向，具体细节在开发前结合案例和开源方案决定。

- 编辑时看到接近正式页面的效果，预览尽量复用真实页面的渲染来源。
- 目标交互是在后台编辑环境中，从预览的标题、图片、介绍、设施等区域进入对应编辑面板，让用户知道修改将出现在哪里；公开详情页不增加这些编辑交互。
- 图片、设施、活动流程等重复项目支持需要的增删和排序；中英共用项目身份与顺序，遵循 BUG-002。
- 页面大区块沿用现有前台模板；可视化编辑改进内容输入方式，不重新设计公开页面布局。本轮未决定提供自由拖拽整页布局、自由 CSS、贴纸或任意代码。
- 继续沿用已确认的“保存并预览”及未保存状态提示。参考站的实时更新、自动保存、撤销等可供研究，尚未全部纳入首版承诺。
- 手机端以编辑／预览切换作为初步方向；具体断点、面板和导航在草图中确认。
- 每个编辑页明确作品、世界、经营者 persona、草稿／送审／公开版本，以及本次可执行的操作。

FEATURE-001 已提供保存并预览、真实页面内嵌、语言与宽度切换；第一阶段工作台在此基础上补齐栏目定位与三类内容编辑。更细粒度的任意元素点击编辑及第二阶段作者入口仍不在当前实现范围。

## 评价与回复的延续和预留

现有实现支持同角色同条目一篇评价，以及每篇评价一条提供者回复。提供者回复已经存在，重构须保留；普通 persona 之间反复对话尚未实现。

用户明确要求预留多轮回复接口。开发前的数据与接口评估应考虑一篇评价对应多条回复、被回复内容／persona、分页、每条发言的权限与审核、历史署名和旧单条回复兼容。这里只确定扩展方向，不提前锁定接口地址、树形结构或迁移方案，也不在第一步自动上线自由讨论串。

角色资料仍由网站管理员审核，世界管理员处理本世界评价／回复。跨世界角色、固定送审版本、历史署名与旧凭条保护继续有效。BUG-001 的独立角色送审与申请替代规则已在第一阶段实现，仍待用户体验验收。

已确认：**整体设计一次完成，分两步实施。** 该决定形成于设计交接时；其后用户已授权并完成第一阶段实现。第二阶段尚未授权启动。

| 步骤 | 交付范围 | 边界 |
| --- | --- | --- |
| 第一步：重构现有操作体验 | 工作台框架、角色管理、评价与已有提供者回复、现有作品编辑流程的可视化改造，解决这些流程依赖的已记录问题 | 保留功能与权限；普通创作者尚未打通的作品入口不能通过放宽世界管理权限临时开放 |

### 实测范围与区别

- 已通过网页读取检查首页和三个工具；通过临时浏览器检查点评工具桌面与手机页面。
- 点评工具中修改对象名称，预览标题立即变化；撤销恢复原名称。390px 视口下当次页面文档宽度为 390px。截图只保存为本机临时研究产物，不作为项目设计资产。
- 关闭教程后的手机截图显示上方为预览，下方为带“内容／样式”标签的编辑面板，顶部保留预览定位按钮；这是可比较的移动端方案，尚未据此替换 Plotstay 初步提出的编辑／预览切换设计。
- 侧栏表单与实时画布已核实；“点击任意预览字段双向定位编辑器”未完整核验，不能称为案例已实现或已测试的通用能力。
- 点评工具允许作者填写示意评分、评论与互动数字；Plotstay 的发布评价均分、他人发言及权限须继续由真实业务数据决定，不能把全部评论当成房东可任意改写的页面字段。
- 当次页面可见服务器导出入口，会说明临时发送成品渲染；本轮未上传、导出或验证其服务端行为。不能笼统宣称所有操作永远不离开浏览器。
- Plotstay 的服务器保存、入驻权限、审核发布、双语与不可变历史继续承担业务约束；本地生成器的保存／导出流程不直接替代这些流程。

优先参考内容分组、以成品为中心的编辑、预览定位、列表选中状态、图片裁切与清楚的保存反馈。案例的模板切换、自由配色与贴纸不纳入本轮前台改动；导出、自动保存和复杂撤销机制先记录为研究点，逐项判断用途。未来 persona 主页可参考设定卡的资料组织，本轮不据此添加所有设定卡字段或公开页面。

开发前以同一住宿作品和任务链比较：在后台预览中选中页面区域 → 编辑中英内容／图片／重复项目 → 保存 → 真实页面预览 → 提交／发布。首先检查能否保持现有前台模板与行为，再评估固定结构约束、移动端与键盘操作、现有内容兼容、数据往返无丢失、版本冲突、权限与草稿隔离、维护活跃度、许可证及必要功能的收费边界。

同时保留“在现有编辑表单与真实预览上增加区域定位”的自定义方案作为比较基线。当前工程采用 Astro、TypeScript、独立 API 与 PostgreSQL，已有版本／审核／历史实现；本轮没有决定迁移 CMS 或安装任何候选依赖。

## 开发拆分与验收要求

以下保留原实施要求；实际任务状态见[WS-00 至 WS-13](workspace-handoff/tasks.md)。交接包的局部原型验证不等于已部署第一阶段的技术回归，更不等于用户体验验收。

1. **盘点现有操作。** 列出角色、作品、评价／回复、审核、预览、发布、下架、恢复等已有入口与权限；建立新旧入口对应，避免布局重构丢失功能。已有入口级迁移清单和关键页面草图；WS-00 开工时继续核对到操作级。
2. **完成后台草图与编辑器评估。** 先覆盖概览、我的作品、单件作品编辑，再覆盖角色、互动、申请与世界管理；明确已确认规则、首批新增能力和仅预留功能。按上面的案例与开源评估标准确定方案。
3. **按两步范围实现。** 第一步以已有权限和流程为基础重构体验；第二步增补世界创建、入驻与作品授权。新增状态和数据按实际盘点做增量衔接，保留现有世界、内容和用户的有效权限，不把旧数据默认改成未审核或未入驻。
4. **验证后台任务链。** 覆盖中英、桌面／手机、不同权限账号、会话过期保留输入、保存与提交区分、退回重提、已发布内容修改、版本冲突、越权拒绝和历史保护；第二步再覆盖世界及入驻流程。
5. **检查前台保持现状。** 实施前在同一内容数据下留存前台基线，按实际影响范围比较中英桌面／手机的首页、列表、三类详情、评价与回复、预订和凭条。检查样式、布局、文案、导航、语言切换和已有功能；后台专属控件、CSS 与依赖不得泄露到公开页面。内容发布验证采用隔离测试数据，避免把测试内容变化误判成改版或改写既有正式数据。
6. **交付与部署。** 汇报后台改动、功能与前台回归验证、未完成项和开发站更新状态；代码修改验证通过后按操作手册部署。不得将仅改源码或仅做后台测试当成已完成交付。
