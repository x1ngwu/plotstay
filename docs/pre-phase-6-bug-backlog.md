## BUG-001：角色审核入口与重复送审

### 用户反馈与现状

用户创建角色后认为已提交审核，但在管理后台找不到对应角色的审核入口；另需明确第一次尚未审核时，用户修改后再次提交应如何处理。

代码核对结果（基于 `494504e`，不是修复后的行为）：

- “我的角色”只有“保存角色”，保存实际创建资料草稿；缺少审核决定时，列表笼统显示“资料待审核”，没有区分未提交与已提交。
- 角色目前主要随评价／回复一同送审。后台链接为“角色评价与回复审核／创建账号”，审核列表以评价为入口，进入具体评价才看到“仅批准角色资料”等操作；缺少明确、独立的角色待审列表。
- `savePersona` 保存新草稿时会清空 `submitted_revision_id`，而审核函数仍可根据旧版本的送审事件批准它。当前待审指针与历史送审资格没有形成统一规则。
- 评价／回复保存角色版本及署名快照，修改角色不会直接改写这些快照。现有实现防止较旧版本后批准时覆盖较新的公开资料，但没有“重新提交后旧待审申请失效”的规则和界面说明。
- 原后台的共用资料管理也能操作角色版本；未来修复必须统一各入口的审核规则，不能只修“我的角色”页面。

### 已确认的处理规则

同一角色至多有一份**当前待审申请**；草稿、待审版本与当前已批准资料分别保存和展示。

| 场景 | 目标行为 |
| --- | --- |
| 新建角色并保存 A 版 | 仅保存草稿，显示“未提交”，不进入待审列表 |
| 提交 A 版 | A 成为当前待审申请，显示“待审核”，管理员能在角色列表直接找到 |
| A 待审时修改并保存 B 版 | B 是新草稿，A 仍待审；用户能看出“有未提交修改”和当前送审内容 |
| 用户再次提交 B 版 | B 成为当前待审申请；A 标记“已被新版替代”，保留历史，不再允许批准或退回 A |
| 重复提交同一版本 | 幂等处理，不产生重复申请或多条有效待审记录 |
| 管理员仍打开 A 的审核页面，B 已重新提交 | 服务端阻止对 A 的过期审核，提示资料已更新，需重新查看 B；不能自动把对 A 的操作应用到 B |
| 管理员先完成 A 的审核，用户随后提交 B | 保留 A 的真实审核结果，B 作为下一次申请；不能把已完成的决定改写成“被替代” |
| 已获批角色再次修改／送审 | 审核通过前继续使用原已批准资料；草稿、待审或退回均不覆盖原公开资料 |
| 当前申请被退回 | 保留退回原因，用户修改、保存新版本后可以重新提交 |

用户端提供清晰的“保存草稿”和“提交审核”操作。保留原“角色与评价一同送审”的便捷路径，且与独立角色送审使用同一套申请与版本规则；不要求先批准角色才能开始写评价草稿。

### 关联评价、回复与历史

- 已发布评价／回复继续保留发表时的名字、头像和角色资料版本，历史凭条不改变。
- A 尚未批准就被 B 的重新提交替代时，仍引用 A 的未发布评价／回复显示“角色资料已更新，需要更新署名并重新送审”。保留正文和原快照，不丢弃用户输入。
- 更新署名需要用户明确操作、保存新内容版本并预览，然后重新提交；不能自动把待审内容的角色快照换成 B，也不能批准 B 后顺带放行引用未批准 A 的内容。
- 同一角色可能在多个条目、不同世界的待审内容中出现，关联状态必须完整覆盖，不能只处理触发这次修改的一篇评价。
- 已经批准的历史资料版本及其历史内容继续有效；“被新版替代”针对尚未完成审核的申请，不追溯撤销旧的批准结果。
- 角色资料仍由网站管理员审核；世界管理员仅审核其世界的评价／回复，不能因增加角色审核入口而扩大权限。

### 具体修复方案（待开工）

1. **统一申请与状态模型。** 在保留不可变资料版本、审核决定及事件历史的基础上，明确草稿指针、当前待审指针、当前批准版本和申请替代关系。保存草稿不撤销现有待审申请；重新提交才替代旧申请。用户资料查询返回这些状态和对应审核说明，避免仅靠“是否存在决定”推断待审。
2. **补齐提交与查询接口。** 提供角色独立提交、管理员角色待审列表和申请详情；列表显示角色名、所属账号、提交时间和状态，详情展示本次中英资料及与已批准版本的差异。联合送审复用同一提交逻辑，已批准且未修改的版本不重复送审。
3. **服务端统一审核校验。** 以角色为单位串行处理提交、替代与审核，在同一事务中校验待审版本、记录替代／审核事件并更新指针。管理员提交操作必须携带其实际查看的申请／版本标识。过期操作返回明确冲突，前端保留审核说明并要求重新查看。独立审核、评价联合发布、回复审核及旧共用资料管理都需执行相同校验。
4. **补齐用户界面。** “我的角色”区分“未提交”“待审核”“已批准”“已退回”，同时展示“有未提交修改”等附加状态；可查看当前送审内容、当前已批准资料和历史申请。中英文提示明确说明保存与提交的区别。
5. **补齐后台入口。** 在管理后台提供名称明确的“角色审核”入口和独立待审列表，网站管理员无需先找到一篇评价才能处理角色；评价／回复审核页面保留关联角色申请入口，并提示过期引用。
6. **处理关联内容与既有数据。** 在未发布内容的查询、预览、送审和发布检查中识别被替代的角色申请，提供更新署名／重新提交路径。实施前只读盘点现有角色、送审事件、决定与引用关系；必要时增量迁移并记录状态衔接，保留原始版本、审核历史和所有已发布快照，不重跑 seed、不重置数据。具体表结构、迁移编号和旧待审记录衔接明细留开工盘点后确定。

## BUG-002：中英重复项目排序不联动

### 用户反馈与现状

后台不论内容类型，中文侧“关键词”点击上移／下移后，英文侧对应项目没有同步移动；“亮点”以及其他有上下移动按钮的地方也存在同类不对齐问题。范围应覆盖所有相关列表，不能只修关键词。

代码核对：`admin.ts` 为每种语言分别创建一份表单数据并调用 `structuredFields`；`structured-fields.ts` 的数组移动只交换当前语言数组中的两个位置。当前设计将文本列表视为各语言独立列表，未建立跨语言的项目对应与共用顺序。图片 ID 等已有稳定引用不能在排序时改成按下标关联。

### 目标与具体方案（范围已确认，待开工）

1. **明确同一项目的中英对应。** 同一个关键词、亮点、设施、步骤或规则的各语言文字归属于同一项目，共用稳定项目标识与顺序。编辑某种语言的文字只改该译文；在任一语言上移／下移则移动整个项目及所有语言对应内容。
2. **盘点全部排序入口。** 检查关键词、亮点、包含项目、服务项目、设施、须知、流程、睡眠安排、图文步骤、资质、安全信息、周边条目等重复字段，以及共用资料表单中的排序控件。图片和场次等本来共用的数据只操作一次；不把不同栏目之间的列表误当作翻译对照。
3. **建立可靠映射再同步。** 有稳定 ID 的项目按 ID 对应；没有 ID 的旧字符串数组／对象数组需补充稳定映射及版本内共用顺序。不能仅凭“两个列表长度相同”或每次的当前下标断言译文对应。旧数据已经错位、缺项或无法确定语义对应时，提供对照校订及缺译提示，保留原值，不自动猜测、丢弃或覆盖译文。
4. **统一表单状态与持久化。** 排序操作同时更新所有语言的编辑状态、隐藏字段与保存载荷，并标记未保存；重绘另一侧时保留尚未保存的输入和焦点。保存、重新打开、语言切换、栏目／高级 JSON 模式切换、导入与后续翻译都必须保留项目标识及顺序，不能保存后重新错位。
5. **关联增删规则。** 结构增删以共用项目为单位：新增建立各语言译文位置并标明缺译；删除明确提示影响全部语言。仅清空某种语言的文字只表示该语言缺译，不删除另一种语言的内容或共用项目；不自动生成译文。具体操作文案可在实现时细化。
6. **保留历史版本。** 仅在新草稿／必要增量迁移中建立映射；不重写旧发布快照，不重新发布现有内容，不默认 seed。数据结构和兼容转换需在实施前完成字段清单后确定。

主要代码范围：`apps/web/src/lib/admin.ts`、`structured-fields.ts`、`settings-editor.ts`，以及相关内容契约、保存／导入／翻译与版本读取逻辑。若引入结构元数据，需同步审查 `packages/contracts` 和数据兼容方案。

### 后续验收标准

- 住宿、活动、服务及手记的相关列表，从任一语言上下移动后，另一语言对应项目顺序同步；文字、图片、图标及子字段归属正确。
- 连续移动、首尾边界、嵌套列表和重复文本均不串项；以项目身份而非显示文字区分重复项。
- 另一语言存在未保存输入、缺译或项目数量不同的情况下，不丢数据，不静默配错；无法确定对应时给出可操作的校订提示。
- 保存重读、预览、发布、恢复历史以及编辑模式切换保持对应；手机语言切换与桌面双栏行为一致。

## BUG-003：评分填写与自动计算的口径不清

### 用户反馈与已核实机制

用户询问后台允许填写评分，而机制又自动计算，二者冲突应如何处理。本轮先核对现状、记录建议，不据此擅自变更评分算法。

| 当前字段／位置 | 数据来源 | 现有行为 |
| --- | --- | --- |
| 单篇手记／评价的总分 `attributes.rating` | 创作者或有权限的后台编辑填写 | 可选 1–5 整数；该评价发布后作为汇总输入 |
| 单篇评价的 `reviewRatings` 分项 | 创作者或有权限的后台编辑填写 | 每项独立输入；按已发布版本参与对应维度计算 |
| 条目评价区的总分、各项均分、分布、评分人数 | `publishedDetail` 对当前已发布评价计算 | 不由后台直接覆盖；未评分项不当作 0 分；回复不计分 |
| 住宿房东卡片的 `hostRating`、`hostReviewCount` | 后台填写的人物叙事统计 | 当前没有按角色关联条目自动汇总；后台标为叙事统计，前台仍显示“评分／条评价”，有混淆风险 |

因此，单篇评分是计算输入，条目总分是计算结果，两者本身可以共存。需要解决的是编辑界面没有清晰说明输入与结果，以及人物卡片的手填数据容易被误认为同一套自动统计。此次核对的路径没有发现自动替用户生成单篇评分的机制；用户所指的具体输入框若另有位置，后续继续补充。

### 处理方案（评分口径已确认，待开工）

1. **把输入和结果分开标识。** 单篇字段明确标为“本篇评价评分”，说明仅该篇发布后参与条目统计；条目总分、评价数量及分项汇总只读，并说明来自哪些已发布评价。后台录入评价不等于直接修改条目均分。
2. **保持单一汇总来源。** 条目评分始终由符合公开条件的当前评价版本计算；不能同时提供一个可随意覆盖的“条目总分”字段。草稿／待审修改不影响公开评分；发布、下架和恢复时按当前公开集合更新。保留已有同角色同条目一篇、分项独立统计等规则，不悄悄增加权重或生成补足评分的评价。
3. **明确人物卡片口径。** 保留 `hostRating`、`hostReviewCount` 等后台填写的人物叙事统计，在前后台清楚标为“人物设定／叙事数据”，避免与条目评价的站内自动汇总混称。本批不增加跨条目提供者汇总，也不把人物叙事数值显示为站内真实评价统计。
4. **保留原数据并提示来源。** 按已确认口径调整前后台字段和显示，不直接清空旧叙事数值或历史内容。预览中标明当前统计来源，避免预览一篇未发布评价时误以为它已改变公开均分。

主要代码范围：`apps/web/src/pages/[locale]/admin.astro`、`apps/web/src/lib/admin.ts`、`structured-fields.ts`、`apps/web/src/components/detail/stay/Host.astro`、`Reviews.astro`、`packages/domain/src/detail.ts` 及相关评分字段契约。现有规则参考 [5.5 管理方案](phase-5-5-content-management.md)与 [5.6 角色评价规则](phase-5-6-persona-reviews.md)。

### 后续验收标准

- 单篇 4 分和另一篇 5 分发布后，条目汇总为 4.50；未评分评价不拉低均分，分项只统计实际有值的评价，提供者回复不影响分数。
- 修改草稿不改公开结果；发布、下架、恢复后结果与公开评价集合一致。
- 编辑者可辨认“可填写的单篇分数”“自动计算结果”和人物叙事数据来源；空状态、计数和中英文名称一致。
- 人物卡片保留手填叙事统计；前后台明确标示来源，不与条目自动汇总混用，原数值保留。

## BUG-004：点击筛选结果“编辑”后没有定位反馈

### 用户反馈与现状

按用户描述理解为后台筛选后的内容结果列表：点击“编辑”后，配置表单在页面下方打开，但页面没有自动下滑，用户容易误以为卡死或按钮无效。

代码核对：列表按钮调用 `openContent` 载入数据并展开 `editor-panel`，没有主动滚动到编辑窗口或移交焦点。该函数也被保存／刷新等操作复用，不能在函数末尾无条件加滚动，导致每次保存都跳页。

### 具体修复方案（待开工）

1. 列表点击“编辑”后显示加载状态，成功载入并完成表单布局后滚动到编辑面板标题，使条目名称和主要操作可见。
2. 将键盘焦点移交给可聚焦的编辑标题或合适入口，并给出“正在编辑：条目名称”反馈；尊重减少动画设置，手机和桌面均可到达。
3. 仅由列表主动打开条目时触发定位；保存、切换版本、局部刷新及表单校验失败不无故把编辑者拉回顶部。保留原有未保存修改确认。
4. 连续点击不同条目时避免请求乱序覆盖；加载失败时恢复按钮并在可见位置显示原因，不滚动到陈旧表单或暗示加载成功。保留筛选条件、分页和列表上下文。

主要代码范围：`apps/web/src/lib/admin.ts` 的 `refreshList`、`openContent`，以及后台编辑面板标题／提示样式。

### 后续验收标准

- 筛选不同内容类型和翻页后点击编辑，实际编辑对象、面板标题和焦点正确，表单进入视口。
- 鼠标、键盘、手机、减少动画设置均有明确反馈；慢请求和失败不被误认为无响应。
- 快速切换条目不会加载成错误对象；取消放弃未保存修改后停留原表单，保存过程不意外跳动。

## FEATURE-001：方便查看修改效果的页面预览

### 用户需求与已有能力

用户希望有页面预览，以便清楚看到修改后的效果。当前已具备受保护的已保存草稿预览：后台“打开已保存草稿预览”在保存后生成中英链接，链接打开真实详情模板；有未保存输入时按钮禁用。共用资料也有基于指定引用条目的配置预览。

本项按“让预览更直观、易发现、操作更连贯”记录；现有已保存草稿预览继续复用。用户已确认本批先做保存并预览，不做未保存内容实时预览。

### 实现方案（范围已确认）

1. **直接可见的入口。** 在编辑窗口提供清楚的“页面预览”，同时显示当前草稿是否已保存、预览语言和版本。预览入口与 BUG-004 的编辑定位一起考虑，避免藏在长表单下方。
2. **提供“保存并预览”。** 有修改时明确执行保存草稿，保存成功后打开／刷新预览；无修改时直接查看当前保存版本。保存失败、会话失效或版本冲突时保留输入，不能展示旧画面却声称为当前修改。保存与审核／发布分离，预览不自动发布。
3. **便于对照。** 建议桌面提供编辑旁的预览区域或可展开预览，手机提供编辑／预览切换，并保留完整新页面入口；可切换中文／英文及桌面／手机宽度。具体布局待审阅，不默认为用户已选定。使用真实详情组件、样式与字体，不维护一份容易脱节的模拟页面。
4. **覆盖实际编辑对象。** 住宿、活动、服务预览对应详情页；评价预览至少展示该条评价的实际卡片与署名，若展示父条目上下文须明确区分草稿与已发布内容。共用资料预览选择真实引用页面并说明影响范围；不默认把该需求扩展成全站任意页面搭建器。
5. **明确动态数据边界。** 预览标明草稿身份。公开评分、已发布评价等关联数据按真实来源显示，未发布草稿不会改变它们；若以后提供发布后的模拟统计，需要明确标记并另定规则，与 BUG-003 对齐。
6. **沿用访问保护。** 复用现有后台权限、版本／翻译 token 检查、Basic Auth、no-store 和 noindex；新面板或新路由不得绕过这些设置。预览不创建预订、评价发布或其他业务副作用，链接过期时提示重新保存／打开。
7. **本批不做实时预览。** 未保存内容不边输入边预览；不做自动保存或每次按键创建数据库版本。若以后另提实时预览需求，再单独设计临时载荷、权限与清理机制。

主要代码范围：`apps/web/src/lib/admin.ts`、`settings-editor.ts`、后台页面及样式、`apps/web/src/pages/api/admin/preview/[locale]/[id].astro`、`packages/domain/src/detail.ts` 的 `previewDetail`；继续复用三类详情组件。

### 后续验收标准

- 修改并保存后能直接看到对应条目、语言、版本的真实布局；BUG-002 的排序结果和图片关联在中英预览中一致。
- 未保存状态、保存中、失败、冲突和预览过期清楚可见，不误用旧版本画面；切换预览语言／宽度不丢表单输入。
- 已保存的同一草稿在预览区域与独立预览页内容一致；公开页在审核发布前保持原版本。
- 手机、桌面和键盘可操作；预览受原有访问控制，不能绕过审核发布或产生预订。

## FEATURE-002：图标选择与图形预览

### 用户需求与现状

用户希望选择 icon 时能看到实际图形，例如 `bath`，方便判断选中图标的含义与显示效果。

代码核对：后台共用 `structured-fields.ts` 将图标枚举当作普通文字下拉选项，没有显示 SVG 图形；部分选项缺少中文名称，仍显示 `bath` 等标识。前台 `Icon.astro` 已有对应 SVG 路径，`stayIconSchema` 定义了可选范围，可直接复用现有图标体系。

### 具体方案（待开工）

1. **选择前可看图。** 将相关 icon 字段统一接入图形选择器，每个选项显示实际图标和易懂名称，例如“浴缸（bath）”。建议采用可展开的图标网格／列表，具体外观沿用现有后台风格。
2. **选中后立即预览。** 收起选择器后仍显示当前图标和名称，切换时即时更新，无需先保存或打开整页预览；保留明确的选中状态和中英文标签。
3. **与前台使用同一份图形。** 提取或复用已有 SVG 定义、尺寸比例与描边样式，让后台预览与实际页面一致；不另画一套近似图标，不增加新的图标库或上传功能。底层继续保存稳定图标标识，显示名称随界面语言变化。
4. **覆盖所有相关字段。** 盘点设施、亮点、安全信息等可选图标的位置，统一使用同一选择器。只在图标字段展示图形，不把全部枚举下拉都转换为图标控件。旧值／未知标识不得因打开表单被静默改成其他图标。
5. **与排序和页面预览衔接。** 图标随所属项目移动，BUG-002 的跨语言排序不得错绑图标；FEATURE-001 的页面预览应呈现同一选中图形。仅切换本地预览不自动保存或发布。
6. **基本可用性。** 桌面、手机均可选择，键盘可操作；每项有可读名称，选中状态不只靠颜色表达。

主要代码范围：`apps/web/src/lib/structured-fields.ts`、`apps/web/src/components/detail/stay/Icon.astro`、图标契约及后台样式；必要时抽取共享 SVG 定义供前后台使用。

### 后续验收标准

- 选择前能看到 `bath` 等各候选项的真实图形；选择后立即显示正确图标和名称。
- 初次载入、修改、保存重读、项目排序及页面预览均保持同一图标，不丢失其他表单输入。
- 图标选项与字段允许的枚举一致，中英名称正确，未知旧值有提示且不被静默覆盖。
- 所有相关图标字段行为一致，手机及键盘操作可用；与前台图形一致，不改变公开页面直到正常审核发布。
